## 1. 決策與目標

先保留 Firestore＋Realtime Database，完成既有同步流程的修正。順序為：建立可比較的量測 → 移除無效提交與投影副作用 → 統一財務交易 → 原子建立共享事件 → 實測 → 必要時才拆分共享資料。

最優先是玩家完成操作後結果正確、全場可繼續，接著降低延遲和不必要讀寫。不能以延長防抖、刪除交易防護、忽略同步錯誤換取表面上的用量下降。

本輪不變更遊戲規則、牌庫、家庭歷程資格或財務公式。關閉重開、重新登入、跨裝置恢復、暫時離開和執行師投影都必須納入驗收。

## 3. 修改邊界與資料責任

| 資料 | 正式來源與寫入方式 | 本機用途 |
|---|---|---|
| 現金、資產、負債、收入、支出、幸福結果 | Firestore 私人玩家文件；經驗證的原子交易 | 呈現與輸入預覽，不把舊整份資料當成交易結果覆寫 |
| 回合、落點、卡片與事件進度 | Firestore 房間／既有 boardState | 動畫與操作中狀態 |
| 共享名單、回覆、完成結果 | 既有共享 prompt 與玩家結果，先維持現有結構 | 依正式狀態顯示待辦 |
| 在線／離線 | RTDB 連線、斷線偵測 | 連線提示 |
| 操作端／只讀端 | 既有控制權機制，所有寫入入口遵守 | 操作是否可用；投影不競爭控制權 |
| 名稱、選擇草稿、畫面偏好 | 沿用現有帳號／草稿儲存 | 可防抖保存；只寫擁有的欄位 |
| 歷史 | 正式結算／交易結果 | 分頁展示，不常駐反覆讀取全部 |

本輪先不新增服務、第三方套件或 Firestore 集合。沿用 runRoomBoardMutation、transaction、既有 ID 與 Rules；有需要的內部拆檔限於明確責任，不全面重寫 Context。

## 4. 階段 0：固定基準與最小量測

### 執行動作

1. 確認實際 dev 工作樹、SHA、未提交差異、正式 deployment、Firebase project、資料库區域與 Rules 雜湊。保存既有差異；測試中不得混入另一個正在修改的版本。
2. 以相同三玩家測試資料準備「靜置、普通回合、共享卡片、家庭歷程、主持補助、重連」短劇本。
3. 檢查所有 transaction／batch／setDoc／updateDoc 入口。列出交易類型、改哪些文件、是否更新房間、是否有本機回寫、是否需要控制權。
4. 在既有交易入口增加可關閉、有限長度的本機測試紀錄；沿用既有遙測管道做採樣摘要。禁止每個操作再寫一筆 Firestore 診斷文件。
5. 修正目前 duplicate、未提交也一律標記 committed 的遙測。分開記錄 committed、duplicate、no_change、rejected、failed。

### 紀錄欄位

- 操作種類、測試用事件代號、版本、耗時、錯誤碼。
- 外層重試次數、transaction callback 執行次數，兩者不可混為一談。
- callback 嘗試讀取文件數、最後提交預計寫入文件數；標記為程式側計數，不宣稱是完整計費數。
- 點擊、提交、回傳成功／失敗、其他頁收到正式快照、顯示視窗的時間。
- 不記密碼、token、完整財務文件或可識別個資。

單一頁面耗時用單調時鐘；跨頁面時間不得直接相減未校準的裝置時鐘。自動化測試由同一測試端對所有頁面的事件接收時間計時，雲端實測則記錄校時方式與誤差。

### 完成條件

能重播同一劇本並比較結果；已區分「設計上的動畫等待」「網路提交」「交易重試」「畫面呈現」。未取得基準時可以繼續修正確定錯誤，但不可宣稱百分比成效。

## 5. 階段 1：移除不必要提交與投影副作用

### 1A. 無變更不提交

主要檔案：src/game/board/runBoardMutation.ts、src/context/RoomContext.tsx、src/game/board/boardRevision.ts。

- 逐一檢查 mutate 的提前返回。事件已過期、修復已由他人完成、沒有任何變更時明確 commit:false。
- 不以 result:false 自動判斷：玩家拒絕參與是有效回覆，仍須提交。
- 修復 ID 以場次／事件／修復種類辨識，不以每次變動的 revision 製造新修復工作。
- 處理殘留 family_milestone request 的修復必須真正移除符合條件的舊請求；不得因沒有 stale prompt 就回傳原狀態，留下反覆觸發條件。
- 清除時重新驗證目前事件與請求，避免刪除同 UID 後來建立的新請求。
- 同一修復進行中先避免重入；重連後仍從正式狀態判斷，不只靠本機旗標。

驗收：殘留請求 fixture 可修復一次；修復後靜置 10 分鐘沒有 revision 自增；重送同一修復無財務或事件副作用。

### 1B. 投影頁只讀

主要檔案：src/App.tsx、src/views/board/BoardProjectionView.tsx、src/context/RoomContext.tsx。

- 在一般遊戲 Provider 掛載前分流 boardRoom 路由，保留必要 Auth、錯誤呈現及房間讀取。
- 不在投影頁啟動玩家財務存檔、全部玩家私有文件監聽、控制權 claim 或主持人自動修復。
- 若投影內已有合法主持操作，先盤點並移回操作端，不能無意移除功能。
- 投影登入狀態與一般頁共用既有帳號機制；投影可在另一台已授權裝置觀看，不因此取得操作權。
- 音訊、骰子和卡片顯示維持既有功能。

驗收：反覆開啟、重整及關閉兩個投影頁，執行師操作頁始終可操作；投影沒有私人財務監聽或交易提交。

### 1C. 相同快照不引起資料重算

- 資料內容與連線 metadata 分開處理。保留離線／重連顯示，不對相同資料重新合併整份 room。
- effect 依賴穩定的 uid、roomId、session 標記；避免只因 user 物件重新建立便重新查歷史或立即備份。
- 保留需要的 listener，不以輪詢或每隔數秒重訂閱取代即時同步。

驗收：metadata-only 更新可改連線提示，但不產生財務回寫；同房同帳號的 listener 數不因普通 render 持續增加。

## 6. 階段 2：統一財務交易，防止舊資料回寫

主要檔案：src/context/GameContext.tsx、src/context/RoomContext.tsx、src/hooks/useGameLogic.ts、src/views/game/GameView.tsx 及相關財務元件。

### 執行動作

1. 先完成 caller 清單：股票買賣、定存及解約、信貸／強制負債、房市與抽卡購屋、保險、醫療、家庭歷程、分享核准、企業貸款／升級、主持調整及補助。
2. 每項標記目前是「已原子提交」「本機修改後自動同步」「混合」，並建立前後金額與待辦預期。
3. 逐項把正式多人財務操作接到既有 transaction：讀取最新私人玩家文件，驗證目前場次／事件／資格／金額，再一次更新結果、歷史和必要完成狀態。
4. 隨該項遷移完成，移除對應本機權威回寫。全部依賴查清前，不整段刪除 GameContext 同步 effect。
5. 通用保存只保存玩家設定與草稿的所屬欄位；不再附帶整份 cash、assets、liabilities 等金融結果。
6. 交易 callback 不顯示彈窗、不播放動畫、不變更 React 狀態，也不在每次重試重新生成一次新的隨機結果；成功提交後才顯示結果。
7. 結果回傳區分成功、已完成、資金不足、事件過期、權限／連線失敗。失敗保留輸入，不顯示已完成。
8. 以穩定操作 ID 重送同一意圖；新的一次合法購買／交易才使用新 ID。不能每次重試生成新 ID。

### 重連與防重

- 交易已提交、畫面尚未收到就關閉：重開從正式文件恢复結果，重送不再扣款。
- 尚未成功提交即斷線：保持待辦；恢復後重新確認，不依賴本機「已完成」旗標結案。
- 新局清空上一局選擇與暫存，核對 room.startedAt／場次標記；同局保留座位、資產與進度。
- 只讀分頁禁止所有自動財務回寫。已在途的合法 transaction 以正式結果恢復，不能假設切換控制權會撤銷已提交交易。
- UI 控制權判斷不是防作弊安全邊界。涉及控制端驗證時，要確認现有 Rules 可驗證的依據；RTDB 狀態不會自動被 Firestore Rules 跨服務讀取。若需要新增持久控制欄位，另列相容變更，不假裝前端 guard 已提供伺服器驗證。
- 最近 100／200 筆 ID 只是快取；歷史 ID 被截掉後，仍須以當局事件、持久完成狀態與有效資格拒絕舊操作。

### 完成條件

每一項財務功能都有前後資料驗證；同時主持補助與玩家交易後兩者效果都保留；遠端快照重放不觸發財務反寫；關頁與重送不產生半套資產或重複貸款。

## 7. 階段 3：共享事件一次建立與可靠結案

主要檔案：src/context/RoomContext.tsx、src/views/game/GameView.tsx、src/game/board/*、必要時的 firestore.rules。

### 原子建立

- 翻牌 transaction 同時建立該卡需要的家庭／一般共享 prompt、有效目標名單與卡片日誌。
- 從 transaction 最新房間及牌庫取得規則，金額與資格不以畫面傳入內容為權威。
- 執行師發卡與自然踩格抽卡最後共用同一翻牌入口；發卡不提前執行玩家財務效果。
- 動畫僅控制揭示時間。斷線或關頁不會留下必須由動畫回呼才建立的正式事件。
- 已揭示但缺少必要 prompt 的舊事件，用同一冪等建構邏輯恢復；必須先辨別「尚未建立」與「已完成清除」，不得重新打開已結案事件。

### 保留既有家庭歷程規則

- 抽卡者直接選擇參與／放棄。
- 其他有效玩家每個事件只擲一次，≥4 點才可選擇參與。
- 每位玩家依自己的五階段進度結算，放棄不推進個人階段。
- 未達標、放棄、已完成全部階段，都要有明確完成狀態，不能留在等待名單。
- 財務結果與該玩家完成回覆同筆提交；所有必要動作完成後，卡片結案一次。
- 有剩餘步數就恢復移動，沒有剩餘事件才開放結束回合。

### 一般共享卡片

- 同樣統一目標名單、玩家回覆、正式效果和完成條件。
- 第三位玩家尚未收到視窗時仍保留其待辦；重連可恢復。
- 暫時離線不移出名單。執行師明確移除或跳過才由正式操作記錄如何處理，不讓在線狀態自動改變遊戲結果。
- 玩家已回覆但交易失敗時不可標記完成；拒絕參與則屬已回覆。

### 完成條件

3／6 位玩家同時操作、抽卡者先完成／最後完成、最後完成者為非抽卡者、來源玩家翻牌後關頁等情境均可恢復並結案。日誌一筆、財務效果一次、完成後舊視窗不復活。

## 8. 階段 4：縮小資料與 UI 更新範圍

此階段先做有明確收益的項目，不為拆檔而拆檔。

- 玩家歷史預設最近 20 筆，使用游標載入更多；同 timestamp 排序增加穩定次排序，避免重複或漏筆。需要新索引時與發布清單一起管理。
- GM／執行師報表分頁；全域統計不能只把目前頁的筆數當成總人數。保留完整搜尋需求，不能只搜尋已載入頁卻宣稱搜尋全站。
- 讓棋盤和私人財務呈現依不同資料更新；先量測不必要 render，再採最小組件／Context 分離。
- 大地圖每 80ms 動畫更新限縮到動畫組件，卡片、人物資料和整份地圖不跟著重算。
- 非必要報表／圖表依功能載入；分包僅作載入效能改善，不列為 Firestore 寫入節省。
- 統一非必要歷史上限前，先確認完整歷史的產品需求與保存位置；不能為省資料把使用者需要的紀錄靜默刪除。

驗收：手機、執行師操作頁、大地圖的必要資料不延遲；歷史分頁無重複漏筆；幀率／長任務與載入大小有前後比較。

## 9. 可選後續：拆開共享回覆文件

啟動條件：上述修正完成後，6 人同時回覆仍因同房間文件競爭超出延遲門檻，且 trace 已確認瓶頸。

候選設計：每個事件有穩定事件文件，各玩家回覆分開保存；本人財務＋本人回覆原子更新；回合與結案由目前有權限的控制端以同一結案 ID 提交。每位回覆不再改同一房間／事件共用回覆計數器，否則只是換位置競爭。

這涉及 schema、Rules、索引、讀取扇出、舊場次相容与控制端離線恢復，需另成遷移規格。只要交易仍讀頻繁變動的房間文件，也可能继续競爭，不能只拆寫入位置就宣稱解決。

每位玩家即時回覆需可查證；最後控制端重連可從已保存回覆恢復結案。不要依賴一台永遠在線的主持電腦，也不要讓所有客戶端無限制輪流重試結案。

同時比較讀取、寫入、重試、傳輸與延遲；拆文件可能增加讀取數，只在整體結果符合目標時採用。

## 10. 測試與用量驗收

### 本地測試順序

1. 在未修改前用最小 fixture 重現無變更提交、缺 prompt、舊財務回寫等問題，保存結果。
2. 每階段新增／調整最相關的單元測試與 Emulator 競態測試。
3. Emulator 使用獨立 project／端口或獨立設定檔，測試前確認端口來源；不得清空使用者正在手測的 Emulator。工具連線必須確認本地端點，避免 seed 或 clearFirestore 指向雲端。
4. 3 位玩家＋1 位執行師＋投影，使用獨立瀏覽器 context 測試；先完成短劇本。
5. 6 位玩家＋1 位執行師＋投影重跑，共 8 個頁面。允許指定卡片準備資料，但回覆、財務、結案由正式 UI 執行。
6. 最後執行 TypeScript、相關與完整 Vitest、Rules、正式 build、git diff --check。測試失敗記錄原因，不改成略過後宣稱通過。

### 必測矩陣

| 情境 | 應驗證結果 |
|---|---|
| 靜置 10 分鐘 | 無持續 room revision／財務寫入；排除預期備份與連線事件 |
| 全員同時家庭擲骰 | 每人一骰、不覆蓋、失敗不可重擲 |
| 抽卡者／參與者最後完成 | 正確結案及換回合 |
| 融資、保險、定存、買賣、貸款／升級 | 現金、資產、負債、收入、支出與歷史一致 |
| 補助與玩家交易同時 | 雙方結果保留，不回退 |
| 翻牌建立途中斷線 | 恢復必要 prompt，未完成卡片不消失 |
| 提交後立即關閉 | 已成功不再執行；未成功保留待辦 |
| 同帳號另一裝置登入 | 新控制端恢復，舊端停止新寫入 |

## 11. 發布與回復方式

1. 每階段保持可獨立檢查的差異與測試證據。使用目前 dev 工作樹時保留既有內容；有其他工作進行中先辨識重疊，避免混入未驗收版本。
2. 第一批發布包含已驗收的無效提交、投影、財務與共享流程修正；未完成的資料拆分不混入。
3. 更新系統日誌只列已完成項目，版本以當時對外版本遞增，不在此計畫先假設仍停留 v3.6。
4. 若 Rules／索引有變更，先驗證新舊前端相容，再發布相容規則／索引與前端；正式 build 確認連雲端，local emulator 設定獨立保留。
5. 首次上線安排場次間空檔；已有玩家可能仍使用快取舊 JS。短期允許相容的舊局完成，新局用新版本。不能以「已部署」假設每位玩家都已更新。
6. 保存舊 deployment ID、Rules 版本與資料格式。遇到重複入帳、資料回退、權限錯誤或卡片永久等待，停止擴大測試，保存證據後回復相容版本。
7. 前端 rollback 不會還原玩家資料，也不會自動還原 Rules。若已變更 schema，需有對應回復策略；錯誤財務修復另做可核對調整，不能拿舊房間快照整份覆蓋。
