## Purpose

本文件定義銀行事件、銀行服務窗口、定存、貸款入口、保險入口與金融服務的正式設計。

本文件只承接 `docs/spec/PRODUCT_SPECIFICATION.md` 與已確認 Decision，不重新定義產品規則。

## Scope

### 本文件負責

- 定義銀行事件的正式責任
- 定義銀行服務窗口的正式責任
- 定義定存的正式入口與完成條件
- 定義貸款入口的正式入口與完成條件
- 定義保險入口的正式入口與完成條件
- 定義金融服務的正式分類與權限邊界

### 本文件不負責

- 重新定義銀行以外的棋盤事件
- 重新定義股票交易規則
- 重新定義汽車購買規則
- 重新定義資產估值規則
- 重新定義負債結構細節
- 重新定義理賠規則

### 邊界原則

- 銀行事件只負責一次銀行觸發所對應的正式流程。
- 銀行服務窗口只負責可辦理服務的時間性權限。
- 定存、貸款入口、保險入口只承接已確認的正式規則，不在本文件重寫產品規則。
- 所有與財務成立相關的規則，必須以財務檢核完成為正式成立條件。

## Definitions

| 名詞 | 定義 |
|---|---|
| 銀行事件 | 玩家經過或停留銀行格時觸發的一次性正式事件。其正式流程包含月結餘與服務選擇。 |
| 銀行服務窗口 | 玩家因銀行事件取得的時效性服務權限。其有效期從經過銀行開始，一直到自己下一回合正式開始前。 |
| 月結餘 | 銀行事件中固定先處理的月結算步驟。其正式內容由上游財務規則定義。 |
| 定存 | 需要銀行服務窗口才能辦理的正式資產入口。開立與解約都必須通過財務檢核。 |
| 貸款入口 | 借款與還款的正式操作入口。其權限屬常駐金融功能，不受銀行服務窗口限制。 |
| 保險入口 | 醫療、房屋、汽車保險的正式購買入口。其購買權限依銀行服務窗口規則決定。 |
| 金融服務 | 由銀行系統承接的正式金融操作集合，包含定存、貸款入口與保險入口。 |
| 財務檢核 | 正式交易成立前的必經檢查。未通過時，交易不得正式成立。 |

## State

| State 名稱 | 用途 | 進入條件 | 離開條件 | 允許操作 | 禁止操作 |
|---|---|---|---|---|---|
| 待觸發 | 尚未進入銀行正式流程 | 尚未觸發銀行事件，且沒有正在處理中的銀行流程 | 玩家經過或停留銀行時離開 | 等待銀行事件觸發 | 辦理定存、保險入口、金融服務成立 |
| 銀行事件進行中 | 正在處理單次銀行事件 | 玩家經過或停留銀行，且銀行事件已觸發 | 月結餘與服務選擇完成後離開 | 月結餘、服務選擇、建立或更新銀行服務窗口 | 視為事件完成、直接失去窗口權限 |
| 銀行服務窗口有效 | 正式服務權限已啟用 | 銀行事件完成且仍在有效期限內 | 玩家下一回合正式開始時離開 | 定存、保險入口，以及可與窗口並存的常駐金融功能 | 重新執行月結餘、使用已失效服務 |
| 金融服務處理中 | 正在辦理單一金融服務 | 玩家選擇定存、保險入口，或在同一銀行流程中辦理常駐貸款入口 | 該服務完成財務檢核並正式寫入後離開 | 該筆服務的正式檢核與成立 | 略過財務檢核、同時混入其他未選擇服務 |
| 窗口失效 | 服務權限已結束 | 下一回合正式開始，或正式期限到達失效點 | 下一次銀行事件觸發時離開 | 等待下一次銀行事件 | 使用需要有效窗口的金融服務 |

## Rules

### 銀行事件規則

- 玩家只要經過銀行或停留於銀行格，都會觸發一次銀行事件。
- 每次銀行事件都必須先處理月結餘。
- 銀行事件完成月結餘後，才可進入銀行服務選擇。
- 銀行事件與銀行服務窗口是兩層不同規則。
- 銀行事件完成，不代表銀行服務窗口立即失效。

### 銀行服務窗口規則

- 玩家每次經過銀行，都會取得一次銀行服務窗口。
- 銀行服務窗口的有效期，從經過銀行開始，一直到自己下一回合正式開始前。
- 銀行服務窗口僅用來判定需要窗口的金融服務是否可辦理。
- 銀行服務窗口內可重複辦理正式金融服務，只要各自通過財務檢核。
- 銀行服務窗口失效後，不得再使用需要窗口的金融服務。

### 定存規則

- 定存辦理屬於正式金融服務。
- 定存辦理需要銀行服務窗口。
- 定存解約不需要銀行服務窗口。
- 定存的開立與解約都必須通過財務檢核後才正式成立。
- 定存的正式結果必須寫入正式交易紀錄。

### 貸款入口規則

- 借款與還款屬於常駐金融功能。
- 借款與還款不需要銀行服務窗口。
- 借款與還款都必須通過財務檢核後才正式成立。
- 貸款入口的正式結果必須寫入正式交易紀錄。

### 保險入口規則

- 醫療、房屋、汽車保險的購買屬於正式金融服務。
- 保險購買需要銀行服務窗口。
- 保險購買都必須通過財務檢核後才正式成立。
- 保險購買結果應依正式資產附掛規則與後續保險系統規則承接。
- 保險購買的正式結果必須寫入正式交易紀錄。

### 金融服務共通規則

- 本文件中的金融服務，只指銀行系統承接且已被正式規則允許的服務。
- 所有金融服務都必須先通過財務檢核，才能正式成立。
- 金融服務完成後，必須留下可追蹤的正式交易紀錄。
- 需要銀行服務窗口的服務，不得以常駐金融功能之名繞過權限。
- 不需要銀行服務窗口的服務，仍須依正式財務規則成立。

## State Machine

| State | Transition | Trigger | Allowed Transition | Forbidden Transition |
|---|---|---|---|---|
| 待觸發 | 進入銀行事件進行中 | 玩家經過或停留銀行 | 待觸發 -> 銀行事件進行中 | 待觸發 -> 銀行服務窗口有效 |
| 銀行事件進行中 | 進入銀行服務窗口有效 | 月結餘完成，且銀行事件本身已完成 | 銀行事件進行中 -> 銀行服務窗口有效 | 銀行事件進行中 -> 窗口失效 |
| 銀行服務窗口有效 | 進入金融服務處理中 | 玩家選擇定存、貸款入口或保險入口 | 銀行服務窗口有效 -> 金融服務處理中 | 銀行服務窗口有效 -> 待觸發 |
| 金融服務處理中 | 回到銀行服務窗口有效 | 該筆金融服務通過財務檢核並正式成立 | 金融服務處理中 -> 銀行服務窗口有效 | 金融服務處理中 -> 待觸發 |
| 銀行服務窗口有效 | 進入窗口失效 | 玩家下一回合正式開始 | 銀行服務窗口有效 -> 窗口失效 | 銀行服務窗口有效 -> 銀行事件進行中 |
| 窗口失效 | 回到待觸發 | 下一次銀行事件尚未觸發 | 窗口失效 -> 待觸發 | 窗口失效 -> 銀行服務窗口有效 |

## Edge Cases

| 情境 | 問題 | 正式處理方式 |
|---|---|---|
| 玩家經過銀行但未使用任何金融服務 | 銀行事件完成後是否仍可保留窗口 | 可以。銀行事件完成後，銀行服務窗口仍依有效期持續存在。 |
| 玩家在同一個銀行事件中連續辦理多個金融服務 | 是否可以共用同一個窗口 | 可以。只要每一筆服務都各自通過財務檢核，且仍在有效期內。 |
| 玩家下一回合正式開始時仍有銀行服務窗口 | 窗口是否仍然有效 | 不可以。窗口在下一回合正式開始時立即失效。 |
| 定存已開立但之後銀行服務窗口到期 | 既有定存是否失效 | 不會。窗口失效只影響之後的辦理權限，不影響已正式成立的定存。 |
| 借款或還款發生時沒有銀行服務窗口 | 是否仍可成立 | 可以。借款與還款屬常駐金融功能，不受窗口限制。 |
| 保險入口被選擇但財務檢核未通過 | 是否可正式成立 | 不可以。未通過財務檢核時，該筆保險入口不得正式成立。 |
| 房屋保險或汽車保險購買成功 | 正式結果應如何處理 | 必須依正式資產附著規則更新對應資產狀態，並留下交易紀錄。 |
| 月結餘完成後玩家不立刻使用服務 | 銀行事件是否仍可完成 | 可以。銀行事件可先完成，銀行服務窗口再持續到失效點。 |

## Design Principles

### 單一職責（Single Responsibility）

- 本文件只負責銀行事件、銀行服務窗口與銀行承接的正式金融入口。
- 本文件不承擔完整財務規則、資產所有權、保險理賠或貸款子系統細節。

### 模組化（Modular Design）

- 銀行事件、銀行服務窗口、定存入口、貸款入口與保險入口集中在本文件定義。
- 各金融服務的下游細則由對應 GDD 承接，不在本文件重複展開。

### 低耦合（Low Coupling）

- 本文件只依賴回合與財務兩個必要上游系統。
- 與資產、保險、貸款的交界只保留正式邊界，不反向定義下游細節。

### 高內聚（High Cohesion）

- 本文件所有章節都圍繞銀行事件、服務權限與銀行承接的正式金融流程。

### 單一權威來源（Single Source of Truth）

- 銀行產品規則以 `docs/spec/PRODUCT_SPECIFICATION.md` 為唯一產品來源。
- 銀行相關拍板結果以已確認 Decision 為唯一決策來源。

### 不可循環依賴（No Circular Dependency）

- 本文件只依賴上游文件。
- 下游子系統若需銀行入口規則，應引用本文件，不得反向讓本文件依賴其細節。

### 依賴方向固定（Top-down Dependency）

- 依賴方向維持為 Product Specification -> Decision -> Core GDD -> Domain GDD。

### 資料與 UI 分離

- 本文件只描述正式資料模型、正式狀態與正式規則。
- 本文件不描述任何畫面、操作元件或呈現方式。

### 規則與實作分離

- 本文件只描述正式設計，不描述任何技術實作。

### 產品規則不得寫進程式

- 本文件承接正式產品規格與已確認決策。
- 實作必須追隨本文件，不得以實作現況覆蓋正式規則。

## Writing Rules

1. 本文件不得重新定義產品規則。
2. 本文件不得包含：
   - Option
   - Recommendation
   - Problem
   - Current Implementation
   - Need Confirmation
   - TODO
   - RFC Analysis
   - Legacy Analysis
3. 本文件不得描述程式碼。
4. 本文件不得描述 Framework。
5. 本文件不得描述 UI 細節。
6. 本文件不得描述 API。
7. 本文件不得描述 Database。
8. 本文件不得重新開啟產品討論。
9. 本文件若引用產品規則，必須直接以上游正式文件為準。
10. 本文件若引用已確認決策，必須直接承接，不得改寫其結論。
11. 本文件不得與其他 GDD 重複定義責任。
12. 本文件若需跨模組規則，必須以引用方式處理。

## Modular Design Rules

- 一個 GDD 只負責一個系統，本文件只負責銀行系統。
- 本文件可依賴多份上游 GDD，但不得反向依賴下游 GDD。
- 本文件不得與其他 GDD 形成循環依賴。
- 每個正式銀行規則只能定義一次。
- 下游 GDD 必須引用本文件中的正式入口與服務窗口規則，而不是複製內容。
- 若規則屬於財務、資產、保險或貸款子系統，必須由對應 GDD 承接。
