# Purpose

本文件負責定義棋盤系統的正式設計，包含棋盤結構、移動規則、格子分類、經過規則、停留規則，以及棋盤事件入口。

本文件不得重新定義產品規則。

所有玩家可感知的正式棋盤規則，皆以上游產品規格與已確認決策為準；本文件只負責將其整理為單一系統的正式設計。

# Scope

## 本文件負責

- 定義棋盤的正式結構
- 定義玩家在棋盤上的移動規則
- 定義格子的正式分類
- 定義經過格與停留格的正式判定
- 定義棋盤事件的正式入口條件
- 定義棋盤系統自身的正式 State 與狀態轉換

## 本文件不負責

- 定義完整回合生命週期
- 定義事件佇列的通用模型
- 定義卡片抽取、揭示與結算細節
- 定義銀行、醫院、學校、維修廠各自的子系統細節
- 定義財務檢核、資產估值、保險、貸款與交易成立規則

## 邊界原則

- 棋盤只負責判定何時進入棋盤事件，不負責重寫各事件的內部規則。
- 經過與停留的正式判定由棋盤系統負責，事件的完成條件由事件系統與各子系統承接。
- 與銀行、卡片、財務、資產相關的下游規則，必須引用對應 GDD，不得在本文件重複定義。

# Definitions

| 名詞 | 定義 |
|---|---|
| 棋盤 | 玩家進行移動與觸發正式格子事件的循環路徑。 |
| 格子 | 棋盤上的單一位置單位，用於承載一種正式格子類型。 |
| 格子類型 | 用於定義該格子在經過或停留時會觸發何種正式規則的分類。 |
| 位置索引 | 用於標示玩家目前所在格子的正式位置編號。 |
| 移動 | 玩家依本回合棋盤移動骰結果，沿棋盤前進的正式過程。 |
| 移動步數 | 本次棋盤移動實際前進的格數。 |
| 移動路徑 | 玩家從起點位置到停留位置之間，依序經過的所有格子集合。 |
| 經過判定 | 玩家移動過程中穿越某格子時，對該格子進行的正式事件入口判定。 |
| 停留判定 | 玩家移動結束後，對最終落點格子進行的正式事件入口判定。 |
| 棋盤事件入口 | 因經過或停留某格子而正式建立事件的條件。 |
| 特殊格 | 具有正式效果或可建立正式事件入口的格子。 |
| 起點 | 所有玩家的初始格，同時作為棋盤循環的基準位置。 |
| 環狀循環 | 玩家移動至最後一格後，下一步回到起點並持續前進的棋盤結構。 |

# Data Model

| 欄位名稱 | 型別 | 用途 | 限制 | 說明 |
|---|---|---|---|---|
| boardSize | 整數 | 定義棋盤總格數 | 必須為固定正整數 | 本系統正式棋盤總格數為 52。 |
| startIndex | 整數 | 定義起點位置 | 必須為有效位置索引 | 本系統正式起點為 0。 |
| playerPosition | 整數 | 記錄玩家目前所在位置 | 必須介於 0 至 51 | 每位玩家同時只能有一個正式棋盤位置。 |
| movementDiceCount | 整數 | 記錄本次棋盤移動使用的骰子顆數 | 僅允許 1 或 2 | 只適用於棋盤移動，不適用於其他事件骰。 |
| movementSteps | 整數 | 記錄本次實際移動步數 | 必須為正整數 | 一顆骰時為單骰點數；兩顆骰時為總和。 |
| movementPath | 格子索引列表 | 記錄本次移動依序經過的格子 | 不得為空 | 用於經過事件與停留事件的正式判定。 |
| landingIndex | 整數 | 記錄本次移動最終停留位置 | 必須為有效位置索引 | 為 movementPath 的最後一格。 |
| tileType | 列舉 | 定義格子正式類型 | 必須為已定義類型之一 | 由本文件統一管理格子分類語意。 |
| passEventTypes | 事件類型列表 | 定義該格子在經過時可能建立的事件 | 可為空 | 僅列出正式經過事件。 |
| landingEventTypes | 事件類型列表 | 定義該格子在停留時可能建立的事件 | 可為空 | 僅列出正式停留事件。 |
| skipTurnCount | 整數 | 記錄玩家尚需略過的未來回合數 | 不得為負數 | 棋盤只承認其結果，不負責產生所有來源規則。 |

# State

| State 名稱 | 用途 | 進入條件 | 離開條件 | 允許操作 | 禁止操作 |
|---|---|---|---|---|---|
| 待移動 | 等待當前玩家開始本次棋盤移動 | 玩家進入可執行移動的回合階段 | 玩家正式擲出棋盤移動骰 | 選擇移動骰顆數、開始棋盤移動 | 直接略過移動、直接建立棋盤事件 |
| 移動中 | 依移動步數建立正式移動路徑 | 已確定本次移動步數 | 移動路徑與最終停留格完成判定 | 計算移動步數、生成移動路徑 | 在路徑未完成前判定停留結果 |
| 經過判定中 | 依移動路徑逐格判定經過事件入口 | 移動路徑已建立且包含經過格 | 所有經過格完成正式入口判定 | 檢查銀行、學校、維修廠等經過條件 | 跳過正式經過判定 |
| 停留判定中 | 對最終落點進行停留事件入口判定 | 經過判定完成 | 停留格完成正式入口判定 | 檢查卡片格、銀行、學校、醫院、維修廠等停留條件 | 在停留判定前宣告棋盤流程完成 |
| 棋盤事件待處理 | 棋盤已完成事件入口建立，等待後續事件處理 | 經過或停留已建立正式棋盤事件 | 該次移動所產生的棋盤事件全部完成 | 將控制權交給事件系統 | 在事件未完成前切換下一位玩家 |
| 棋盤完成 | 本次棋盤移動與其入口判定已全部完成 | 本次棋盤事件全部完成，且無未處理棋盤入口 | 回合結束或下一次合法移動開始 | 結束棋盤階段 | 重複建立同一次移動的棋盤事件 |
| 停回合 | 標示玩家未來回合需略過移動 | 醫院或維修廠等正式效果成立 | skipTurnCount 歸零且新回合開始 | 略過回合中的棋盤移動 | 在停回合期間執行正常棋盤移動 |

# Rules

## 棋盤結構規則

1. 棋盤採固定 52 格循環設計。
2. 所有玩家起始位置皆為起點。
3. 起點的正式位置索引為 0。
4. 起點同時屬於學校格。
5. 棋盤採環狀循環；玩家前進超過最後一格時，依序回到起點繼續計算。

## 格子分類規則

1. 棋盤正式格子類型包含：
   - 起點／學校格
   - 銀行格
   - 醫院格
   - 維修廠格
   - 幸福卡格
   - 機運卡格
   - 新聞卡格
   - 其他無正式事件入口的一般格
2. 格子類型只決定棋盤入口條件，不直接取代下游事件規則。
3. 同一格可同時具有起點與學校的正式語意，但仍須依本文件定義的入口規則處理。

## 移動規則

1. 沒有汽車時，玩家每次棋盤移動只能使用一顆骰子。
2. 擁有汽車時，玩家每次棋盤移動前可自行決定使用一顆骰子或兩顆骰子。
3. 兩顆骰子的總和即為本次移動步數。
4. 棋盤移動骰的選擇僅適用於棋盤移動，不適用於其他事件骰。
5. 每次棋盤移動都必須建立正式移動路徑。
6. 經過判定以移動路徑中的中途格為準。
7. 停留判定以移動路徑最後一格為準。

## 經過規則

1. 正式經過事件格包含：
   - 銀行格
   - 學校格
   - 維修廠格
2. 玩家經過銀行格時，必須建立一次銀行事件入口。
3. 玩家經過學校格時，必須建立一次學校事件入口。
4. 玩家經過維修廠格時，只有在持有汽車的情況下，才建立維修廠事件入口。
5. 非正式經過事件格在經過時不建立正式事件。

## 停留規則

1. 正式停留事件格包含：
   - 銀行格
   - 學校格
   - 醫院格
   - 維修廠格
   - 幸福卡格
   - 機運卡格
   - 新聞卡格
2. 玩家停留銀行格時，必須建立一次銀行事件入口。
3. 玩家停留學校格時，必須建立一次學校事件入口。
4. 玩家停留醫院格時，必須建立一次醫院事件入口。
5. 玩家停留維修廠格時，只有在持有汽車的情況下，才建立維修廠事件入口。
6. 玩家停留幸福卡格、機運卡格、新聞卡格時，必須建立對應卡片事件入口。

## 棋盤事件入口規則

1. 棋盤事件入口分為兩類：
   - 經過入口
   - 停留入口
2. 只要符合正式入口條件，就必須建立對應事件，不得省略。
3. 同一次移動若同時產生多個棋盤事件入口，必須全部保留並依正式事件順序處理。
4. 棋盤事件入口建立後，該回合不得在事件未完成前切換下一位玩家。
5. 棋盤事件入口本身不定義事件內部的支付、抽牌、幸福值、停回合或金融效果；這些內容由下游系統承接。

## 停回合規則

1. 玩家若受到正式效果影響而需要略過未來回合，棋盤系統必須承認該停回合狀態。
2. 停回合中的玩家在被略過的回合中，不執行正常棋盤移動。
3. 停回合只在正式效果成立後生效，不得提前生效。

## 遊戲結束規則

1. 遊戲正式結束後，不再建立新的棋盤移動。
2. 遊戲正式結束後，不再建立新的棋盤事件入口。
3. 玩家達成里程碑不會單獨終止棋盤系統；仍須依正式結束條件判定。

# Flow

```text
開始
  ->
確認玩家是否可進行棋盤移動
  ->
決定本次棋盤移動骰顆數
  ->
擲出棋盤移動骰並取得移動步數
  ->
建立正式移動路徑
  ->
逐格執行經過判定
  ->
對最終落點執行停留判定
  ->
建立本次移動的全部棋盤事件入口
  ->
等待所有棋盤事件完成
  ->
棋盤完成
```

# State Machine

| State | Transition | Trigger | Allowed Transition | Forbidden Transition |
|---|---|---|---|---|
| 待移動 | 進入移動中 | 玩家開始本次合法棋盤移動 | 待移動 -> 移動中 | 待移動 -> 停留判定中、待移動 -> 棋盤完成 |
| 移動中 | 進入經過判定中 | 移動步數與移動路徑已正式建立 | 移動中 -> 經過判定中 | 移動中 -> 棋盤完成、移動中 -> 停回合 |
| 經過判定中 | 進入停留判定中 | 所有經過格已完成正式入口判定 | 經過判定中 -> 停留判定中 | 經過判定中 -> 棋盤完成 |
| 停留判定中 | 進入棋盤事件待處理 | 最終落點已完成正式入口判定 | 停留判定中 -> 棋盤事件待處理 | 停留判定中 -> 待移動 |
| 棋盤事件待處理 | 進入棋盤完成 | 本次移動產生的所有棋盤事件已完成 | 棋盤事件待處理 -> 棋盤完成 | 棋盤事件待處理 -> 待移動、棋盤事件待處理 -> 下一位玩家 |
| 棋盤完成 | 進入待移動 | 新的合法回合開始且玩家可再次移動 | 棋盤完成 -> 待移動 | 棋盤完成 -> 經過判定中 |
| 棋盤完成 | 進入停回合 | 正式效果要求玩家略過未來回合 | 棋盤完成 -> 停回合 | 棋盤完成 -> 移動中 |
| 停回合 | 回到待移動 | 規定略過回合數已消化完畢 | 停回合 -> 待移動 | 停回合 -> 移動中、停回合 -> 棋盤完成 |

# Edge Cases

| 情境 | 問題 | 正式處理方式 |
|---|---|---|
| 同一次移動經過多個正式事件格 | 單一步驟可能產生多個事件入口 | 所有符合條件的經過事件都必須建立，不得只保留最後一個。 |
| 同一次移動同時有經過事件與停留事件 | 經過入口與停留入口可能並存 | 必須先完成正式經過判定，再完成正式停留判定。 |
| 停留在同時具有起點與學校語意的格子 | 單一格具有雙重語意 | 依本文件的格子分類規則，承認其學校入口語意。 |
| 玩家持有汽車但選擇單骰移動 | 汽車不等於強制雙骰 | 仍視為合法棋盤移動，移動步數以單骰點數為準。 |
| 玩家沒有汽車但移動路徑經過維修廠 | 維修廠是否仍建立事件 | 不建立維修廠事件入口。 |
| 玩家停留維修廠但已無汽車 | 停留事件是否成立 | 不建立維修廠事件入口。 |
| 玩家需停回合但前一回合事件尚未完成 | 停回合何時正式生效 | 必須先完成前一回合的正式事件，再於後續回合套用停回合效果。 |
| 玩家達成幸福值里程碑時仍有棋盤事件未完成 | 里程碑與棋盤流程衝突 | 里程碑不會中止當前棋盤流程，仍須完成全部正式事件。 |
| 遊戲正式結束時仍存在未開始的棋盤移動 | 是否可繼續建立新入口 | 不得再建立新的棋盤移動與新的棋盤事件入口。 |

# Design Principles

## 單一職責（Single Responsibility）

- 本文件只負責棋盤系統。
- 本文件不承擔卡片、銀行、財務或個別事件子系統的主責內容。

## 模組化（Modular Design）

- 棋盤系統作為獨立模組，提供移動與格子入口規則。
- 下游系統透過正式入口與棋盤系統銜接，不複製棋盤定義。

## 低耦合（Low Coupling）

- 棋盤只定義入口條件，不重寫下游事件內部規則。
- 與其他系統的依賴以引用方式維持，不在本文件展開非主責細節。

## 高內聚（High Cohesion）

- 本文件所有章節皆服務於棋盤結構、移動、格子與入口判定。
- 不混入非棋盤主責的正式資料模型。

## 單一權威來源（Single Source of Truth）

- 棋盤的正式產品規則以上游產品規格為唯一來源。
- 格子分類、經過判定與停留判定的正式定義以本文件為唯一設計來源。

## 不可循環依賴（No Circular Dependency）

- 本文件只依賴上游核心文件。
- 本文件不得反向依賴學校、醫院、維修廠等下游子系統文件。

## 依賴方向固定（Top-down Dependency）

- 依賴方向必須維持 `Product Specification -> Decision -> Core GDD -> Domain GDD`。
- 棋盤系統位於核心 GDD 層，不得依賴下游 Domain GDD 來定義自身規則。

## 資料與 UI 分離

- 棋盤位置、格子分類與入口條件屬於正式資料與規則。
- 呈現方式不屬於本文件範圍。

## 規則與實作分離

- 本文件只定義棋盤系統的正式設計。
- 任何實作方式都不得取代本文件中的正式規則。

## 產品規則不得寫進程式

- 棋盤規則必須先存在於正式文件。
- 實作只能依據本文件與其上游正式文件進行。

# Writing Rules

1. 不得重新定義產品規則。
2. 不得包含：
   - Option
   - Recommendation
   - Problem
   - Current Implementation
   - Need Confirmation
   - TODO
   - RFC Analysis
3. 不得描述程式碼。
4. 不得描述 Framework。
5. 不得描述 UI 細節。
6. 不得描述 API。
7. 不得描述 Database。
8. 不得重新開啟產品討論。
9. 若 Product Specification 已定義，直接引用。
10. 若 Decision 已 Confirmed，直接引用。
11. 不得與其他 GDD 重複定義責任。
12. 若責任跨模組，必須引用其他 GDD，不得複製其內容。

# Modular Design Rules

- 一份 GDD 只負責一個系統。
- 本文件只負責棋盤系統。
- 本文件可依賴多份上游 GDD，但不得反向依賴下游 GDD。
- 本文件不得形成循環依賴。
- 棋盤系統只能有一份正式 GDD。
- 棋盤的正式入口規則只能在本文件定義一次。
- 下游 GDD 若需使用棋盤規則，必須引用本文件，不得複製內容。
