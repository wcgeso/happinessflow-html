## Purpose

本文件定義醫院系統的正式設計。

本文件只負責說明醫院事件、醫療費、停回合與完成條件的正式規則與正式資料模型。

本文件不得重新定義產品規則。

所有醫院相關正式規則皆以上游產品規格與已確認 Decision 為正式來源。本文件僅承接上游規則，將其整理為醫院系統的正式設計。

## Scope

### 本文件負責

- 定義醫院系統的正式責任範圍
- 定義醫院事件的正式入口與完成邊界
- 定義醫療費的正式語意與處理邊界
- 定義停回合的正式語意與生效邊界
- 定義醫院系統的正式 State 與狀態轉換

### 本文件不負責

- 重新定義回合順序或回合切換規則
- 重新定義棋盤移動與格子分類規則
- 重新定義事件佇列與事件生命週期
- 重新定義財務檢核、交易成立與月結算規則
- 描述任何程式、介面或技術實作

### 邊界原則

- 醫院系統只負責醫院事件本體與其正式結果，不負責改寫回合系統。
- 醫院事件的入口由 `BOARD_SYSTEM.md` 負責，事件生命週期由 `EVENT_SYSTEM.md` 負責，醫療費成立與支付由 `FINANCIAL_SYSTEM.md` 負責。
- 停回合屬正式結果，必須交由回合系統承接，不得在本文件以畫面或提示取代正式規則。

## Definitions

| 名詞 | 定義 |
|---|---|
| 醫院事件 | 玩家停留在醫院格時觸發的正式事件。其正式內容包含醫療費處理與停回合結果承接。 |
| 醫療費 | 由醫院事件產生的正式支出。其成立、支付與交易結果必須由財務系統承接。 |
| 停回合 | 玩家下一個正式回合必須直接略過擲骰與移動的正式效果。 |
| 醫院完成 | 醫院事件本體、醫療費與停回合結果皆已正式處理完畢的狀態。 |
| 醫院擁有者 | 對本次醫院事件具有主要承接責任的玩家。 |
| 完成條件 | 醫院事件可以正式收束所必須同時滿足的條件集合。 |
| 財務成立 | 醫療費已通過正式財務檢核並完成正式結果寫入的狀態。 |

## State

| State 名稱 | 用途 | 進入條件 | 離開條件 | 允許操作 | 禁止操作 |
|---|---|---|---|---|---|
| 待觸發 | 表示目前沒有正在處理的醫院事件 | 玩家停留醫院格之前 | 醫院事件正式成立後離開 | 等待正式事件入口、建立醫院事件基本資料 | 直接宣告醫院完成、直接套用停回合 |
| 醫院事件進行中 | 表示醫院事件已正式成立 | 玩家停留醫院格，且醫院事件已建立 | 進入醫療費處理中或已完成時離開 | 承接醫院事件流程、建立醫療費處理要求 | 切換下一位玩家、略過醫療費 |
| 醫療費處理中 | 表示醫療費正在進行正式財務處理 | 醫院事件已成立且需要處理醫療費 | 醫療費正式成立後離開 | 進行財務檢核、補足支付能力、寫入正式交易結果 | 跳過正式財務檢核、先宣告停回合完成 |
| 停回合標記中 | 表示停回合效果已準備承接，但尚未由回合系統消化 | 醫療費正式成立，且本次醫院事件要求停回合 | 停回合效果已正式寫入回合系統後離開 | 記錄下一次正式回合需略過 | 讓玩家在下一回合正常擲骰與移動 |
| 已完成 | 表示醫院事件已正式結束 | 醫療費與停回合結果皆已正式處理完畢 | 無 | 交還事件完成權、允許回合系統推進 | 再次變更本次醫院事件結果 |

## Rules

### 1. 醫院事件規則

1. 醫院事件只在玩家停留醫院格時觸發。
2. 醫院事件屬正式事件，必須服從事件系統的生命週期與完成條件。
3. 醫院事件完成前，不得切換下一位玩家。
4. 醫院事件若尚未完成，仍屬當前回合責任範圍，不得視為額外例外流程。
5. 醫院事件必須包含一次正式醫院骰點結果。

### 2. 醫療費規則

1. 醫療費屬正式支出，必須納入財務系統處理。
2. 醫療費在正式財務檢核通過前，不得視為已成立。
3. 若醫療費支付能力不足，必須先依財務系統完成補足處理，醫院事件才可正式成立。
4. 醫療費完成後，必須留下可追蹤的正式結果。
5. 醫療費金額固定為醫院事件骰點結果乘以 `1,000`。

### 3. 停回合規則

1. 停回合代表玩家下一個正式回合必須直接略過擲骰與移動。
2. 停回合不得在醫院事件正式完成前先行生效。
3. 停回合的正式承接必須由回合系統處理，本文件只負責提供正式結果。
4. 停回合只作用於下一次輪到該玩家的正式回合，不得無限延伸到後續回合。
5. 醫院事件造成的停回合次數固定為 `1`。

### 4. 完成規則

1. 醫院事件完成必須同時滿足以下條件：
   - 醫院事件本體已正式成立
   - 醫療費已正式成立並完成財務處理
   - 停回合結果已正式寫入回合系統，若本次醫院事件要求停回合
2. 只要任一條件未成立，醫院事件就不得完成。
3. 醫院事件完成後，才可進入下一位玩家或下一正式回合。

### 5. 交界規則

1. `BOARD_SYSTEM.md` 只負責醫院格的正式入口，不負責醫院事件內部細節。
2. `EVENT_SYSTEM.md` 負責醫院事件的排隊、完成與阻塞模型。
3. `FINANCIAL_SYSTEM.md` 負責醫療費的正式成立、補足與交易紀錄。
4. `TURN_SYSTEM.md` 負責把停回合結果轉成下一次正式回合的略過效果。

## Flow

```text
開始
  ->
玩家停留醫院格
  ->
建立醫院事件
  ->
進入醫院事件進行中
  ->
擲一次醫院事件骰
  ->
處理醫療費
  ->
完成財務檢核
  ->
醫療費正式成立
  ->
若本次醫院事件要求停回合
  ->
寫入停回合結果
  ->
醫院事件已完成
  ->
交還回合系統
  ->
完成
```

## State Machine

| State | Transition | Trigger | Allowed Transition | Forbidden Transition |
|---|---|---|---|---|
| 待觸發 | 進入醫院事件進行中 | 玩家停留醫院格且正式事件入口成立 | 待觸發 -> 醫院事件進行中 | 待觸發 -> 已完成 |
| 醫院事件進行中 | 進入醫療費處理中 | 醫院事件已成立且需要處理醫療費 | 醫院事件進行中 -> 醫療費處理中 | 醫院事件進行中 -> 已完成 |
| 醫療費處理中 | 進入停回合標記中 | 醫療費正式成立且本次事件要求停回合 | 醫療費處理中 -> 停回合標記中 | 醫療費處理中 -> 已完成 |
| 醫療費處理中 | 進入已完成 | 醫療費正式成立且本次事件不要求停回合 | 醫療費處理中 -> 已完成 | 醫療費處理中 -> 停回合標記中（若本次事件要求停回合） |
| 停回合標記中 | 進入已完成 | 停回合結果已正式寫入回合系統 | 停回合標記中 -> 已完成 | 停回合標記中 -> 醫療費處理中 |
| 已完成 | 無下一正式狀態 | 醫院事件已正式結束 | 無 | 重新回到待觸發或醫療費處理中 |

## Edge Cases

| 情境 | 問題 | 正式處理方式 |
|---|---|---|
| 玩家停留醫院格但醫療費尚未完成 | 是否可先結束事件 | 不可以。醫療費是醫院事件的一部分，未完成前不得收束。 |
| 醫療費支付能力不足 | 是否可直接完成醫院事件 | 不可以。必須先依財務系統完成補足處理後，醫院事件才可正式成立。 |
| 醫院事件要求停回合，但回合尚未交接 | 停回合何時生效 | 必須先完成醫院事件，再由回合系統在下一次正式回合套用停回合效果。 |
| 同一回合內仍有其他正式事件 | 醫院事件是否可先切換下一位玩家 | 不可以。醫院事件必須依事件系統完成後，才可結束當前回合。 |
| 玩家已達幸福里程碑 | 醫院事件是否可因此省略 | 不可以。里程碑不會中止醫院事件或回合流程。 |
| 遊戲已正式結束 | 是否可再建立醫院事件 | 不可以。遊戲正式結束後不得建立新的醫院事件。 |

## Design Principles

- 單一職責：本文件只定義醫院事件、醫療費、停回合與醫院完成條件。
- 模組化：棋盤入口、事件生命週期、財務成立與回合略過效果分別引用上游系統，不在本文件重複定義。
- 低耦合：本文件不承擔回合切換、棋盤移動、交易成立主流程或其他格子事件責任。
- 高內聚：所有醫院事件進入、醫療費、停回合與收束規則集中於本文件。
- 單一權威來源：醫院系統正式規則以上游 Product Specification 與 Confirmed Decision 為準。
- 不可循環依賴：本文件只能依賴回合、事件、棋盤與財務系統，不得反向要求它們依賴本文件。
- 依賴方向固定：醫院系統承接上游入口與生命週期，並把停回合與交易結果交由上游系統承接。
- 資料與 UI 分離：本文件只描述正式醫院資料與規則，不描述畫面與操作元件。
- 規則與實作分離：本文件不描述技術流程與執行細節。
- 產品規則不得寫進程式：醫院規則調整必須先更新正式規格。
