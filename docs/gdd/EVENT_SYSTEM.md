## Purpose

本文件定義事件系統的正式設計，負責說明事件如何建立、如何排入佇列、如何進入不同事件層級、如何完成，以及事件完成前如何阻塞回合推進。

本文件不得重新定義產品規則。

所有事件是否觸發、哪些事件屬於正式事件、事件完成前不得切換下一位玩家、卡片必須先揭示再生效等產品規則，一律以 Product Specification 與已確認 Decision 為準。

## Scope

### 本文件負責

- 定義事件系統的正式責任範圍
- 定義正式事件層級
- 定義事件生命週期
- 定義事件佇列規則
- 定義事件完成條件
- 定義後續事件的正式承接方式
- 定義事件狀態機

### 本文件不負責

- 重新定義回合順序
- 重新定義棋盤格效果
- 重新定義卡片內容
- 重新定義財務規則
- 重新定義銀行服務內容
- 描述任何畫面、介面或操作元件

### 邊界原則

- 回合開始、回合結束、跳過回合屬於 `TURN_SYSTEM.md`
- 格子進入條件與移動來源屬於 `BOARD_SYSTEM.md`
- 抽牌、揭示、結算內容屬於 `CARD_SYSTEM.md`
- 銀行事件內容與銀行服務窗口屬於 `BANK_SYSTEM.md`
- 本文件只定義上述流程何時成為正式事件，以及事件如何被推進與完成

## Definitions

| 名詞 | 定義 |
|---|---|
| 事件 | 會改變正式遊戲流程，且在完成前可阻塞回合或阻塞後續流程的正式單位 |
| 共享棋盤事件 | 由棋盤移動或卡片鏈建立，所有玩家都必須承認其存在與完成結果的正式事件 |
| 共享事件樣態 | 不是獨立事件本體，但需要多位玩家共同等待或共同回覆後才可收束的正式共享狀態 |
| 在地事件流程 | 附屬於正式事件之下的局部處理流程，本身不是獨立正式事件，不能單獨推進回合 |
| 事件佇列 | 用來保存待處理正式事件的有序集合 |
| 目前事件 | 事件佇列中當前正在處理的唯一正式事件 |
| 後續事件 | 由前一事件正式產生，且必須在前一事件完成鏈中接續處理的事件 |
| 事件擁有者 | 對該事件具有主要處理責任的玩家 |
| 事件完成 | 事件本身、其必要後續結果、其必要結算條件皆已結束的狀態 |
| 事件阻塞 | 因事件尚未完成，而禁止回合切換或禁止下一事件開始的正式限制 |
| 揭示 | 正式公開事件內容，且揭示前不得生效的階段 |
| 結算 | 依正式規則套用事件結果的階段 |
| 收束 | 事件完成後，自事件系統退出並交還流程控制的階段 |

|---|---|---|---|---|
| eventQueue | 事件列表 | 保存待處理正式事件 | 必須保持有序；同一時間只能有一個目前事件 | 正式事件佇列 |
| currentEvent | 事件物件或空值 | 表示當前正在處理的正式事件 | 不可同時存在多個目前事件 | 由佇列前端取得 |

| eventType | 列舉 | 標示事件種類 | 只能使用正式事件類型 | 例如銀行、學校、醫院、維修廠、卡片、後續卡片 |
| eventLayer | 列舉 | 標示事件層級 | 只能是共享棋盤事件、共享事件樣態、在地事件流程之一 | 用來界定責任與阻塞力 |
| ownerPlayerId | 文字 | 標示事件擁有者 | 正式事件必須有唯一擁有者 | 家庭共同參與例外由共享事件樣態承接回覆 |
| source | 來源描述 | 記錄事件由何種規則產生 | 不得留空 | 例如經過格子、停留格子、前一張卡片 |

| revealRequired | 布林值 | 表示事件是否必須先揭示 | 為真時不得跳過揭示 | 卡片與市場相關事件需先揭示 |
| blockingScope | 列舉 | 標示事件阻塞範圍 | 只能是阻塞回合、阻塞事件鏈、僅阻塞自身完成 | 用來決定何時不可前進 |
| followUpEvents | 事件列表 | 保存由本事件產生的正式後續事件 | 後續事件必須在本事件完成前處理完畢 | 屬於正式事件鏈的一部分 |
| sharedResponses | 回覆列表 | 保存共享事件樣態所需的多方回覆 | 僅共享事件樣態可使用 | 例如共同參與結果 |
| completionRule | 規則描述 | 定義事件何時可視為完成 | 不得與上游規格衝突 | 用來驗證事件是否可收束 |
| completionResult | 結果描述 | 保存事件完成後的正式結果 | 僅能在結算後寫入 | 供下游流程引用 |

## State

| State 名稱 | 用途 | 進入條件 | 離開條件 | 允許操作 | 禁止操作 |
|---|---|---|---|---|---|
| 待建立 | 代表事件尚未進入正式事件系統 | 事件來源已成立，但尚未排入正式佇列 | 建立事件並排入佇列 | 建立事件基本資料 | 直接生效、直接切換回合 |
| 已排隊 | 代表事件已進入正式佇列等待處理 | 事件被加入事件佇列，且尚未成為目前事件 | 事件被推進為目前事件 | 保留事件順序、等待前置事件完成 | 跳過前置事件、直接結算 |
| 進行中 | 代表事件已成為目前事件 | 事件從佇列前端被取出並開始處理 | 進入揭示、等待回覆、結算或完成 | 執行該事件允許的正式流程 | 啟動下一事件、切換下一位玩家 |
| 已揭示 | 代表事件內容已正式公開 | 事件要求先揭示，且揭示已完成 | 進入結算或等待必要回覆 | 套用揭示後可進行的後續流程 | 揭示前生效、略過揭示 |
| 等待回覆 | 代表事件需等待其他玩家或必要回覆 | 事件進入共享事件樣態，且仍有未完成回覆 | 所有必要回覆完成 | 接收合法回覆、維持等待 | 提前收束、切換下一位玩家 |
| 結算中 | 代表事件結果正在依正式規則處理 | 揭示完成，且事件開始套用結果 | 所有結果處理完成 | 執行正式結果、建立後續事件 | 略過結果、提前標記完成 |
| 等待後續事件 | 代表本事件已產生正式後續事件鏈 | 結算後產生至少一個正式後續事件 | 所有後續事件完成 | 推進後續事件鏈 | 在後續事件未完成前收束 |
| 可完成 | 代表事件本體與必要後續均已結束 | 完成條件全部滿足 | 正式收束 | 驗證完成條件、關閉事件 | 再次揭示、再次結算 |
| 已完成 | 代表事件已正式結束 | 事件完成並收束 | 交還流程控制 | 允許事件系統推進下一事件或交還回合流程 | 重新開啟同一事件 |

## Rules

### 事件層級規則

1. 事件系統正式分成三層：
   - 共享棋盤事件
   - 共享事件樣態
   - 在地事件流程
2. 共享棋盤事件是正式事件本體，具備獨立進入、排隊、完成與阻塞能力。
3. 共享事件樣態不是獨立事件本體，但屬於正式事件的一部分，會阻塞來源事件完成。
4. 在地事件流程只服務於正式事件完成，本身不得獨立取得事件擁有權，也不得單獨推進回合。

### 正式事件類型規則

1. 正式共享棋盤事件至少包含：
   - 銀行事件
   - 學校事件
   - 醫院事件
   - 維修廠事件
   - 卡片事件
   - 後續卡片事件
2. 家庭歷程卡片事件本體屬於正式事件；其共同參與回覆階段屬於共享事件樣態，不是獨立共享棋盤事件。
3. 任何由正式事件產生的後續卡片，都屬於正式事件鏈的一部分，不得視為例外流程。

### 事件佇列規則

1. 所有正式共享棋盤事件都必須先進入事件佇列，再成為目前事件。
2. 同一時間只能有一個目前事件。
3. 事件佇列必須依正式產生順序處理。
4. 前一事件未完成時，後一事件不得開始。
5. 後續事件仍然必須遵守佇列規則，不得直接繞過正式事件佇列。

### 揭示規則

1. 需要揭示的事件，必須先揭示，後結算。
2. 卡片事件與市場相關事件，在揭示前不得生效。
3. 揭示屬於正式事件生命週期的一部分，不得跳過。

### 完成規則

1. 事件完成必須同時滿足以下條件：
   - 事件本體流程已完成
   - 必要揭示已完成
   - 必要結算已完成
   - 必要共享回覆已完成
   - 必要後續事件已完成
2. 若事件仍有未完成的共享事件樣態，來源事件不得完成。
3. 若事件仍有未完成的後續事件，來源事件不得完成。
4. 事件完成前，不得切換下一位玩家。

### 阻塞規則

1. 正式事件未完成時，必須阻塞回合切換。
2. 正式事件未完成時，必須阻塞下一正式事件開始。
3. 共享事件樣態未完成時，必須阻塞來源事件完成。
4. 在地事件流程若為完成必要條件，則來源事件在其完成前不得完成。

### 後續事件規則

1. 後續事件是由前一事件正式產生的事件，不是額外附註。
2. 後續事件必須遵守與一般正式事件相同的生命週期要求。
3. 學校事件產生的幸福卡、卡片產生的後續卡、其他正式派生事件，都屬於後續事件。
4. 後續事件全部完成後，來源事件才可進入可完成狀態。

### 事件擁有權規則

1. 一般正式事件由事件擁有者負責處理。
2. 家庭歷程共同參與期間，各符合資格玩家只能回覆屬於自己的共同參與結果。
3. 非事件擁有者不得處理他人的正式事件本體。
4. 共享事件樣態的其他玩家回覆權，僅限於完成自身回覆，不等於取得來源事件所有權。

### 遊戲結束規則

1. 遊戲正式結束後，不得再建立任何新事件。
2. 遊戲正式結束後，不得再揭示事件。
3. 遊戲正式結束後，不得再結算事件。
4. 遊戲正式結束後，不得再建立任何後續事件。

## Flow

```text
開始
  ->
事件來源成立
  ->
建立正式事件
  ->
排入事件佇列
  ->
成為目前事件
  ->
若需要，先揭示
  ->
執行正式結算
  ->
若需要，等待共享回覆
  ->
若產生後續事件，排入並完成後續事件鏈
  ->
驗證完成條件
  ->
事件收束
  ->
推進下一事件或交還回合流程
  ->
完成
```

## State Machine

| State | Transition | Trigger | Allowed Transition | Forbidden Transition |
|---|---|---|---|---|
| 待建立 | 建立事件 | 正式事件來源成立 | 已排隊 | 已揭示、結算中、已完成 |
| 已排隊 | 取為目前事件 | 前置事件完成且輪到本事件 | 進行中 | 已完成、可完成 |
| 進行中 | 進入揭示 | 事件要求先揭示 | 已揭示 | 已完成、可完成 |
| 進行中 | 直接結算 | 事件不需揭示 | 結算中 | 已完成 |
| 已揭示 | 開始結算 | 揭示已完成 | 結算中 | 已排隊、待建立 |
| 結算中 | 進入等待回覆 | 結算中產生共享事件樣態 | 等待回覆 | 已完成 |
| 結算中 | 進入等待後續事件 | 結算中產生正式後續事件 | 等待後續事件 | 已完成 |
| 結算中 | 進入可完成 | 無共享等待且無後續事件 | 可完成 | 已排隊 |
| 等待回覆 | 回覆完成 | 所有必要回覆皆完成 | 可完成、等待後續事件 | 已完成、已排隊 |
| 等待後續事件 | 後續事件完成 | 所有後續事件皆完成 | 可完成 | 已完成、已排隊 |
| 可完成 | 正式收束 | 完成條件驗證通過 | 已完成 | 已排隊、進行中 |
| 已完成 | 推進下一步 | 事件系統交還控制權 | 無下一正式狀態 | 任何重新開啟或回退 |

## Edge Cases

| 情境 | 問題 | 正式處理方式 |
|---|---|---|
| 事件已排入佇列時又產生新事件 | 多事件同時存在 | 新事件必須依正式產生順序排入事件佇列，不得插隊略過前置事件 |
| 事件需要揭示但玩家尚未完成揭示 | 事件可能被誤判可結算 | 揭示前不得進入結算中 |
| 家庭歷程有多位符合資格玩家 | 事件可能被提早收束 | 必須等待所有符合資格玩家完成回覆後，來源事件才可完成 |
| 事件產生多個後續事件 | 完成點不清楚 | 必須完成全部後續事件後，來源事件才可完成 |
| 玩家拒絕共同參與 | 共享等待可能卡住 | 拒絕參與屬於正式有效回覆，可用來滿足等待條件 |
| 事件結果需要先完成必要結算 | 事件與結果分離 | 必須等必要結算完成後才可進入可完成 |
| 同一事件被重複觸發 | 事件重複建立 | 同一事件來源只能建立一次正式事件，重複來源不得形成重複事件本體 |
| 遊戲已正式結束 | 仍可能嘗試建立新事件 | 所有事件入口立即封鎖，不再建立、揭示或結算任何事件 |

## Design Principles

### 單一職責（Single Responsibility）

- 本文件只負責事件系統本身
- 不負責定義棋盤效果、卡片內容、銀行服務內容或財務細節

### 模組化（Modular Design）

- 事件層級、事件佇列、事件完成條件必須可被其他 GDD 單獨引用
- 其他系統應引用事件模型，而不是複製事件規則

### 低耦合（Low Coupling）

- 本文件只保留對回合、棋盤、卡片、銀行的必要依賴
- 不主動承擔其他系統的主責規則

### 高內聚（High Cohesion）

- 本文件所有章節都服務於事件如何開始、如何推進、如何完成這個單一目標

### 單一權威來源（Single Source of Truth）

- 正式事件生命週期、事件層級、事件完成與事件阻塞，以本文件為唯一 GDD 來源

### 不可循環依賴（No Circular Dependency）

- 本文件依賴上游正式產品規則與決策
- 下游系統可依賴本文件，但本文件不得反向承接下游系統責任

### 依賴方向固定（Top-down Dependency）

- 產品規格與已確認決策在上
- 事件系統承接其規則
- 卡片、棋盤、銀行等系統再依賴事件系統

### 資料與 UI 分離

- 本文件只定義正式資料模型與正式狀態，不描述任何介面表現

### 規則與實作分離

- 本文件只描述正式事件規則與正式狀態機，不描述任何實作方式

### 產品規則不得寫進程式

- 正式事件規則必須先寫在產品規格、Decision 與 GDD 中
- 實作只能承接既有正式規則

12. 本文件不描述 Database。
13. 若上游 Product Specification 或 Confirmed Decision 已定義規則，本文件直接引用，不重新開啟討論。
14. 若規則屬於其他 GDD，本文件只界定事件責任與交界，不複製其完整內容。

## Modular Design Rules

1. 本文件只負責一個系統，即事件系統。
2. 本文件可依賴多份上游文件，但不得反向依賴下游文件。
3. 本文件不得與其他 GDD 形成循環依賴。
4. 正式事件生命週期只能在本文件定義一次。
5. 其他下游 GDD 必須引用本文件的事件模型，不得複製事件完成與阻塞規則。
6. 若某規則跨模組，本文件只定義事件責任，其他系統在各自 GDD 中定義自身主責內容。
